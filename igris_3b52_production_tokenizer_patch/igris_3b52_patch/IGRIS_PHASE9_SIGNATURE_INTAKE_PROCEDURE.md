## 1. Scope & Architectural Purpose

This document specifies the operational procedure for receiving, validating, and cryptographically verifying external human governance submissions for Project IGRIS.

Under the IGRIS security model:
1. **Human Exclusive Signing**: Cryptographic signatures may only be generated by authenticated physical human reviewers using hardware security tokens.
2. **Deterministic Canonicalization**: Submission payloads are canonicalized in accordance with RFC 8785 (sorted keys, compact delimiters, UTF-8 encoding) to guarantee reproducible cryptographic validation.
3. **Multi-Layer Cryptographic Binding**: A valid signature cryptographically binds the reviewer identity, assigned role, reviewed source IDs, decision, evidentiary file references, and the bitwise SHA-256 hash of the specific dossier file on disk.
4. **Append-Only Tamper-Evident Audit Chain**: Every intake event (successful or rejected) is recorded in an immutable hash-chained audit log (`HUMAN_APPROVAL_AUDIT_TRAIL.jsonl`).
5. **Fail-Closed Default-Deny Gate**: The production dataset pipeline remains **`LOCKED`** until unanimous (4-of-4) valid signatures are committed.

## 2. Submission Payload Specification

All external human review submissions must conform strictly to `schemas/HUMAN_APPROVAL_SCHEMA_V1.json`.

### 2.1 JSON Schema Fields

| Field Name | Type | Constraint / Regex | Description |
| :--- | :--- | :--- | :--- |
| `submission_id` | String | `^SUB-[A-Z0-9]{8,16}$` | Unique submission identifier (e.g., `SUB-CUST20261117`) |
| `role` | String | Enum | Must be one of `DATA_CUSTODIAN`, `LEGAL_GOVERNANCE`, `SECURITY_PRIVACY`, `CHIEF_ARCHITECT` |
| `reviewer_id` | String | String (>= 3 chars) | Corporate identity identifier of the reviewer (e.g., `CORP-ID-88241`) |
| `key_id` | String | `^KEY-[A-Z0-9_\-]{6,32}$` | Registered hardware key identifier (e.g., `KEY-DATA_CUSTODIAN-FIPS01`) |
| `source_ids` | Array[String] | Array of `^SRC-[A-Z]{2}-[0-9]{2}$` | List of candidate source IDs covered by this review submission |
| `decision` | String | Enum | Must be `APPROVE`, `REJECT`, or `REQUEST_CHANGES` |
| `evidence_references`| Array[Object]| Min 1 item | Objects containing `reference_type`, `reference_uri`, `sha256` |
| `timestamp_utc` | String | ISO 8601 UTC | Exact time signature was generated (e.g., `2026-11-17T12:00:00Z`) |
| `expiry_date_utc` | String | ISO 8601 UTC | Expiration date of approval (maximum 90 days from timestamp) |
| `document_path` | String | Path | Relative or absolute path to the reviewed dossier file |
| `document_sha256` | String | `^[0-9a-fA-F]{64}$` | SHA-256 hash of the exact dossier markdown file |
| `digital_signature`| String | `^[0-9a-fA-F]{64}$` | Hex-encoded HMAC-SHA256 (or Ed25519) cryptographic signature |

## 3. Step-by-Step Submission & Verification Procedure

### Step 1: Human Review & Evidence Inspection
The appointed reviewer opens their assigned dossier (e.g., `REVIEW_DATA_CUSTODIAN_V2.md`) and conducts a line-by-line review of each candidate source ID, cross-referencing:
- Upstream archive URLs and checksums (`DATASET_SOURCE_CATALOG_V3.csv`).
- License terms, Life+60/70 thresholds, and commercial-use evidence (`DATASET_LICENSE_EVIDENCE_V2.csv`, `INDIA_COPYRIGHT_REVIEW.md`).
- PII screening scores and vulnerability classifications (`SECURITY_GAP_REGISTER.md`).
- Architectural vocabulary targets and structural token preservation (`TOKENIZER_DATA_ELIGIBILITY_MATRIX.md`).

### Step 2: Compute Dossier File Hash
The reviewer verifies that the dossier file on disk matches their reviewed copy by computing its SHA-256 hash:
```powershell
Get-FileHash -Algorithm SHA256 REVIEW_DATA_CUSTODIAN_V2.md
```
The resulting 64-character hex string is embedded in the `document_sha256` field.

### Step 3: Construct Payload & Compute Canonical Bytes
The reviewer creates the JSON document excluding the `digital_signature` field. The engine serializes the dictionary to canonical JSON bytes per RFC 8785:
```python
import json

def canonical_json_bytes(data: dict) -> bytes:
    # Exclude digital_signature when serializing the signing payload
    payload = {k: v for k, v in data.items() if k != "digital_signature"}
    raw_str = json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
    return raw_str.encode("utf-8")
```

### Step 4: Hardware Enclave Signing
The reviewer invokes their hardware security token (FIPS 140-2 Level 3 HSM / YubiKey) to sign `canonical_json_bytes` using their private key. The resulting 64-character hex string is populated in `digital_signature`.

### Step 5: Submission Ingestion & Verification Execution
The submission JSON is ingested by the automated verification engine:
```python
from review_intake_verifier import ReviewIntakeVerifier, KeyRegistry

verifier = ReviewIntakeVerifier(key_registry)
result = verifier.verify_submission(submission_data, document_path="REVIEW_DATA_CUSTODIAN_V2.md")

if not result.is_valid:
    print(f"REJECTED: {result.errors}")
else:
    print(f"VERIFIED: Submission {result.submission_id} accepted for role {result.role.value}")
```

### Step 6: Immutable Audit Logging & Quorum Consensus
Upon successful verification:
1. The submission is appended to the tamper-evident audit ledger (`HUMAN_APPROVAL_AUDIT_TRAIL.jsonl`) with cryptographic hash chaining.
2. `QuorumEngine` updates consensus state in `SOURCE_APPROVAL_STATE_V2.csv`.
3. If all 4 roles have approved (`QuorumState.APPROVED`), the source becomes eligible for quarantine ingress.
4. If any single role rejects (`REJECT`), the source transitions to `BLOCKED_REJECTED` and remains permanently barred from the pipeline.

## 4. Error Codes & Rejection Criteria

The intake engine enforces fail-closed validation. The table below lists all possible validation failures:

| Error Code | Rejection Cause | Operational Remediation |
| :--- | :--- | :--- |
| `ERR_INVALID_SUB_ID` | `submission_id` does not match `^SUB-[A-Z0-9]{8,16}$` | Correct submission ID format |
| `ERR_ROLE_UNRECOGNIZED` | Role is not one of the 4 defined enum values | Re-submit with valid governance role |
| `ERR_KEY_NOT_FOUND` | `key_id` is not registered in `KeyRegistry` | Complete Task 2 hardware key registration |
| `ERR_KEY_REVOKED` | `key_id` is present on Certificate Revocation List (CRL) | Hardware token revoked; obtain re-issued key |
| `ERR_KEY_ROLE_MISMATCH` | `key_id` is registered to a different governance role | Use role-appropriate hardware security token |
| `ERR_KEY_EXPIRED` | Submission timestamp exceeds key expiration date | Key expired; request annual key renewal |
| `ERR_APPROVAL_EXPIRED` | Current time is past `expiry_date_utc` | Signatures are valid for max 90 days; re-sign |
| `ERR_UNKNOWN_SOURCE_ID` | One or more source IDs not in candidate catalog | Correct source IDs to match official 32 sources |
| `ERR_DOC_HASH_MISMATCH` | `document_sha256` does not match live file on disk | Dossier was modified or corrupted; re-verify hash |
| `ERR_SIGNATURE_MISMATCH` | Digital signature verification failed | Signature forgery or payload tampered; re-sign |

## 5. Security Restrictions & Anti-Fabrication Safeguards

> [!CAUTION]
> **MANDATORY PROJECT SAFEGUARD**: Under no circumstances may automated scripts, developers, or agents inject synthetic keys into the production `KeyRegistry` or generate mock signatures in production registers.
>
> Doing so is treated as an active red-team security attack (Vector 02: Signature Forgery) and triggers an immediate fail-closed pipeline lockdown.

1. **Production Key Registry Purity**: `KeyRegistry` in production contains zero pre-seeded synthetic keys. Only hardware-attested public keys registered by authorized humans are valid.
2. **Strict Quorum Non-Advancement**: Automated test suites test intake verification using ephemeral, in-memory mock registries. The on-disk production status registers (`IGRIS_PHASE8_SOURCE_APPROVAL_LEDGER.csv`, `SOURCE_APPROVAL_STATE_V2.csv`, `IGRIS_PHASE9_HUMAN_REVIEW_TRACKER.csv`) remain completely untouched by automated tests.
3. **Default-Deny Ingress Gate**: The production access gate remains **`LOCKED`**.
